# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.2.0] — 2026-10-20

The **low-level input layer**: coordinates, drag-and-drop, held buttons and keys, a wheel and keyboard that behave like hardware, real clipboard paste, native `<select>`, file drops and (opt-in, gated) touch. Everything is human-by-default and has a `--raw=true` escape hatch; the new commands are all page-targeted (`--page=<id>`).

### Added
- **Coordinate commands.** `click-at <x> <y>` (`--button`, `--clickCount`, `--hold=<ms>`, `--modifiers=Control,Shift,Alt,Meta`, `--exact`), `hover-at <x> <y>`, and the read-only hit test `element-at <x> <y>` (tag, id, classes, role, name, text, href, box, cursor, **effective** `draggable`, `editable`, a short unique `selectorHint`, and the chain of iframes it drilled through — same- and cross-origin). Input at page coordinates is routed by Chrome into iframes, cross-origin ones included.
- **Coordinate spaces.** `--space=css` (default; what `clientX/clientY` report) or `--space=screenshot` (device pixels measured on a `shot` image; css = px / devicePixelRatio). Points are validated (finite, inside the viewport, `--at` inside the element) and every error states the viewport size, the dpr and the converted css values — the DPR trap (a 150% display makes screenshot pixels 1.5x CSS pixels) is called out in the error itself.
- **Selector commands** `click`, `dblclick`, `rightclick`, `hover` gain `--at=x,y` (an offset inside the element, css or screenshot space; the same tiny landing jitter unless `--exact`); the click family also gains `--hold` and `--modifiers`. Without these flags behaviour is unchanged.
- **Drag.** `drag <from> <to>` (`--from-at`, `--to-at`, `--button`, `--modifiers`) and `drag-at <x1> <y1> <x2> <y2>`. The drag is routed by what is under the start point: an **HTML5-draggable** source (effective `draggable`, incl. `img` and `a[href]`) goes through Playwright's mouse, one awaited move per path point, because patchright only intercepts drags caused by its own mouse; anything else (sliders, canvases, resize handles) uses the coalesced raw-CDP pointer bursts with the button held. Measured on Chrome 149: raw CDP moves over a draggable start a native drag (`dragstart`) but never deliver `dragenter`/`dragover`/`drop`/`dragend`, so the routing is required, not cosmetic. Human drag timing: Fitts x1.4, ~150 ms pre-drag hold, no overshoot, 80–200 ms settle. The response reports `mode: 'html5' | 'pointer'`.
- **Held inputs persist across commands.** `mouse-down`/`mouse-up [--button]`, `key-down <key>`/`key-up <key>` and `release` (releases every button and key, in reverse order, zeroing the modifier mask). `pages` and `state` entries now carry `input: { pointer, held: { buttons, keys }, layout }` so a forgotten hold is visible. A manual drag can be composed from `mouse-down` + `hover-at` + `mouse-up` (HTML5 routing is decided at `mouse-down`). Closing a page releases what it still holds first.
- **`press` reworked** (human by default): keys go through the CDP key emitter with a real-time dwell (Chrome stamps the events, see B5); combos `A+B+C` press modifiers first (40–120 ms leads, via Playwright's keyboard so they are stamped on its mouse events) and release in reverse; new `--hold=<ms>` auto-repeats past an OS-like ~500 ms ± 60 delay with `autoRepeat: true` keydowns every ~33 ms (a held printable key keeps typing: holding `a` in an input types `aaaa…`, like real hardware); new `--repeat=<n>`. Named keys: Shift, Control, Alt, Meta, Enter, Tab, Escape, Backspace, Delete, Insert, Home, End, PageUp, PageDown, Arrow*, Space, F1–F12, plus single characters and physical codes (`KeyA`). Keys the emitter does not know fall back to Playwright's keyboard.
- **`type-focused <text>`**: human typing into whatever is focused (no click); the response says what was focused.
- **`scroll` upgraded**: `up|down|left|right|top|bottom|<px>`, `--dx=<px>`, `--target=<selector>` (human-move the pointer into the element first), `--x=<n> --y=<n>` (move the pointer to a viewport point first). The wheel acts on the **scroll container under the pointer** (nearest ancestor that scrolls on that axis, else the document) and the response reports it: `{ scrolledBy, axis, container: { tag, id, isDocument }, before, after, … }`.
- **Wheel model.** The default wheel is a Windows mouse: whole notches (`deltaY`/`deltaX` in multiples of 100, `deltaMode` 0), mostly one notch per event with the occasional 2–3 in fast flicks, 15–40 ms inside a flick and reading pauses between flicks. A wheel has no partial notches, so the requested distance is approximate and `scrolledBy` is the distance actually moved. **`calibrate-wheel [--seconds=10]`** (human in the loop, like the login bootstrap) records the human's own trusted `wheel` events behind an on-page overlay and stores a machine-wide `<data root>/wheel-calibration.json` (delta histogram, flick lengths, intra-/inter-flick gaps); the scroll engine then samples from it. Fewer than 20 events is rejected. `--simulate=true` is a self-test hook that feeds the recorder through CDP (marked `source: simulated`; refuses to overwrite a human calibration). **Only a human calibration is ever adopted** (`source: 'human'`): a simulated or foreign-source profile is saved but ignored, because learning from our own synthetic events is circular — the default model stays in force, and `state`, `status`, `scroll` and `calibrate-wheel` say which model is active (`wheelModel: 'default' | 'human'`; `state` adds `wheelCalibration: { file, source, createdAt, events, quantum, adopted }`).
- **`shot` upgraded**: `--scale=device|css`, `--selector=<sel>`; the response adds `dpr`, `viewport`, `scroll`, `scale`, `imageSize` (read from the PNG header) and `clip` (the CSS-px rectangle the image covers; the element box with `--selector`). `save-artifact` metadata records the real viewport object instead of `null`.
- **`paste <selector> <text>` / `paste-focused <text>`** (`--from-file=<path>` for long text): a REAL paste — the payload goes to the OS clipboard, a human Ctrl+V (Control via Playwright's keyboard, V via the CDP emitter; Cmd on macOS) makes Chrome fire a trusted `paste` event with `clipboardData` and `beforeinput` `insertFromPaste` (verified in headed Chrome), the field is verified and the user's clipboard is restored. The clipboard is shared with the human and with every nativewright daemon, so it is guarded by a **machine-wide, per-OS-user lock** (`<os.tmpdir()>/nativewright-clipboard.lock` — `nativewright-clipboard-<uid>.lock` on Linux/BSD where `/tmp` is shared — created exclusively, holding `{ pid, page, id, at, hb }`; the holder refreshes `hb` every second, so a slow-but-alive holder is never reaped, while a lock whose pid is dead (or that has had no heartbeat for 15 s) is; a waiter gives up after 10 s and types). It deliberately does **not** live under `NATIVEWRIGHT_HOME`: the clipboard belongs to the OS session, so daemons with different data roots (named profiles under another root, isolated test daemons) contend on the same lock instead of cross-talking. **Only an empty or plain-text-only clipboard is ever touched**: images, file lists, HTML/RTF and anything else are left alone and the text is human-typed instead. Restoration happens only while the clipboard still holds our payload. Clipboard contents are never logged or returned. Headless Chrome has its own in-memory clipboard, so there the text is typed (`method: 'typed'`, `reason: 'headless…'`); so it is when the clipboard is locked by another application (`reason: 'clipboard-unwritable'`), the lock stays busy for 10 s (`clipboard-busy`) or Ctrl+V changes nothing (`paste-no-effect`). Response: `{ method, chars, verified, clipboardRestored, clipboardTouched, lockWaitMs, reason?, detail? }`. Never `paste` a secret: a clipboard manager may record it while it is on the clipboard.
- **Windows paste helper: out of other applications' way.** The long-lived `powershell -STA` helper keeps dispatching window messages while it is idle (it reads stdin on a pool thread and pumps every 200 ms; measured: with the poll at 200 instead of 25 ms the other process's write after a paste still took 3 ms and its read after a `Clear()` 26 ms, because *sent* messages are served inside the CLR's pumping wait and the poll only drains the posted ones, so the longer poll costs no latency and cuts the idle CPU). Measured on Windows 10 with separate processes: after any write the helper's hidden OLE window owns the clipboard, and a helper parked in a blocking stdin read made *every other process's clipboard write* take ~5 s (5016, 5008 ms; 3 ms with a pumping or absent owner); when its last operation was `Clipboard.Clear()` (the restore of an originally empty clipboard) *another process's read* (`GetDataObject`) hung for as long as the owner stayed parked (11059 ms, finished 30 ms after the owner was released; 45 ms with a pumping owner). For the helper's 5-minute life that froze copy in the user's other applications, and daemons pasting at the same time starved each other (observed with three: one real paste, one call hung 28.9 s). Around it: clipboard calls are retried on a 2 s time budget instead of nested counted loops; the helper is started *before* the lock is taken (if it cannot start, the text is typed with `clipboard-unreadable`); calls made inside the lock time out after 10 s; a helper that still owes an answer when the paste ends is killed before the lock is released, and the restore is then tried once through a fresh helper (`clipboardRestored: false` with a `restoreNote` unless the original is confirmed back) — a request that timed out is not left to run after the lock is released.
- **The paste payload stays out of Windows clipboard history and cloud sync.** On Windows the payload carries the registered formats `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory` (0) and `CanUploadToCloudClipboard` (0); the user's own text is restored as plain text without them. A user clipboard that carries any of those formats (password managers set the first) is treated like any other non-text clipboard: never read, never touched. Tools that ignore the flags can still record the payload, so the advice stands: never `paste` a secret.
- **Keyboard layout fidelity (Russian ЙЦУКЕН).** Characters are typed on the physical key of the active layout (`code` and virtual-key code of the key position, `key` = the character); capitals are Shift + the same key. The active layout is tracked per page; when the next character is only typable on the other layout a human **layout-switch chord** (Alt+Shift by default, `NATIVEWRIGHT_LAYOUT_SWITCH=ctrl+shift`) is emitted first, and a character typable on both (`.` is Period on EN, Slash on RU) uses the active layout's key. Characters on neither layout (emoji, CJK, other scripts) go through `Input.insertText` — never a keydown with an empty `code`/keyCode 0, which is what the old fallback produced. Typos use PHYSICALLY adjacent keys, so Russian typos are the Russian letters next to the intended one. Shortcuts (`Control+A`) are pressed by position and never switch layout.
- **`select` is human by default**: a real click opens the native list, ArrowDown/ArrowUp at human cadence (disabled options are skipped) and Enter commit it, and the value is verified (`method: 'keyboard'`; falls back to `selectOption` with `method: 'fallback'` if verification fails). `<select multiple>`: click the first option, Ctrl-click (Cmd on macOS) the others. Values match by value or label. `--raw` is plain `selectOption`.
- **Touch gestures, gated and opt-in**: `tap <selector>`, `tap-at <x> <y>`, `swipe <x1> <y1> <x2> <y2>`, `pinch <x> <y> --scale=<f>` via `Input.dispatchTouchEvent` with human finger paths (frame-paced `touchMove`, varying contact radius and force, staggered two-finger pinch). Measured: Chrome delivers touch events even when `navigator.maxTouchPoints === 0` — a detectable contradiction — so these commands **refuse** unless the page reports touch capability. `NATIVEWRIGHT_TOUCH=1` at daemon start launches a touch-capable browser (`hasTouch`, raised to `maxTouchPoints: 10` on every page).
- **Input modality must match the fingerprint** (the mirror image of the touch gate). `hasTouch` also turns the page into a *touch-only, tablet-class* device — measured on Chrome 149, headed (dpr 1.5) and headless alike:

  | page profile | `maxTouchPoints` | `ontouchstart` | `pointer: fine` / `coarse` | `any-pointer: fine` / `coarse` | `hover: hover` / `none` | `any-hover: hover` / `none` |
  |---|---|---|---|---|---|---|
  | default daemon | 0 | false | **true** / false | **true** / false | true / false | true / false |
  | `NATIVEWRIGHT_TOUCH=1` | 10 | true | false / **true** | **false** / true | false / true | false / true |

  `hasTouch` alone gives `maxTouchPoints: 1` (the daemon raises it to 10 per page with `Emulation.setTouchEmulationEnabled`); `--touch-events=enabled` alone gives `ontouchstart` with `maxTouchPoints: 0` (worse); `Emulation.setEmulatedMedia` cannot override `pointer`/`hover`, so "touch **and** mouse" cannot be expressed. A device that reports `(any-pointer: fine)` false cannot produce `pointerType: 'mouse'` events or a wheel, so on such a page **every mouse-dispatching command is refused** with a clear error — `click`, `dblclick`, `rightclick`, `hover`, `click-at`, `hover-at`, `drag`, `drag-at`, `mouse-down`, `mouse-up`, `scroll` (wheel), `calibrate-wheel --simulate`, and the selector text commands that focus their field with a click (`fill`, `type`, `select`, `paste <selector>`) — **`--raw` included**. What works there: `tap` / `tap-at` / `swipe` / `pinch`, then `type-focused` / `paste-focused` / `press` / `key-down` / `key-up` / `release` for the keyboard (tap the field first), `drop-files`, `element-at`, `shot`. `tap` and `drop-files` bring an off-screen target into view with finger drags (`touch.scrollBy`), never a wheel, and `drop-files` does not move a mouse pointer that does not exist. The converse of the touch gate: normal daemons keep refusing touch, touch-only daemons now refuse mouse.
- **`drop-files <selector> <path>…`** (`--at=x,y`): drops OS files onto a page as if dragged from the file manager — the drag enters from the window edge nearest the target, `dragover`s along a human path, settles, drops (`Input.dispatchDragEvent` with real file paths: trusted events, real `File` objects with name/size/type/content, also fills `<input type=file>`).
- Tests: `test/input.test.js` (+ `test/fixtures/*.html`, served from a child process on two sites so the cross-origin iframe is out-of-process, plus a third origin on `127.0.0.2` where that address is bound) and a much larger browser-less sanity suite (`npm run test:sanity`, which runs the human layer in *virtual time* — a sleep advances a clock, so it neither waits nor depends on the machine). The timing assertions hold on a loaded CI VM: the structural ones (no event dated in the future, nothing on the 15.625 ms timer lattice) never relax, the absolute-latency ones do under `CI`; the tests that need Windows (the PowerShell clipboard helper) skip elsewhere with a reason, and select-all and multi-select follow the platform (Cmd on macOS).

### Changed
- **`dblclick` / `clickCount` are real**: the second click now carries `detail: 2` and the page receives a `dblclick` event (see Fixed).
- `scroll` responses report the container and the *actual* distance moved (`scrolledBy` was the requested value; `top`/`bottom` used to return those words).
- Coalesced pointer bursts now carry the page's current `buttons` mask, `button` name, pressure and `modifiers`, mirroring what patchright's own mouse sends, so a drag's event stream stays consistent with its `mousedown`/`mouseup`.
- Typing now iterates user-perceived characters (an emoji or `é` as `e`+U+0301 is one unit), honours an explicitly held Shift (never presses it twice, never releases it; characters come out shifted, as on hardware) and releases only the Shift it pressed itself.
- A button that is already held cannot be pressed again (an error instead of a second `mousedown`).
- `state` reports `headless` and `touch`. `npm test` runs `test/smoke.test.js` and `test/input.test.js` by name (`node --test test/` fails on Node ≥ 22, which treats the directory as a module path).
- `shot --fullPage=false` is now respected (`!!"false"` used to be true).
- Daemons started with `NATIVEWRIGHT_TOUCH=1` no longer accept mouse commands (see *Input modality* above) — they used to send `pointerType: 'mouse'` events from a device whose media features say it has no mouse.
- `calibrate-wheel` / `state` / `status` report the active wheel model; a non-human calibration file no longer changes scrolling.
- `NATIVEWRIGHT_TOUCH=1` is described (README, `src/touch.js`, `src/daemon.js`) as what it measurably is — a touch-only, tablet-class device with no mouse — not a "touchscreen laptop", which would also report a fine pointer and hover.

### Fixed
- **B1 — wrong viewport.** The context is launched with `viewport: null`, so `page.viewportSize()` is `null`, and `human.js` fell back to 1280×800 while the real viewport was 758×482 (headless) / ~1180×730 (agent windows): wrong in-view decisions (Playwright's programmatic `scrollIntoViewIfNeeded` jump replaced human wheel scrolling), an initial pointer that could start outside the window, and `save-artifact` writing `viewport: null`. The viewport is now measured fresh on every command (`innerWidth`, `innerHeight`, `devicePixelRatio`, scroll) and used by pointer placement, in-view decisions, coordinate validation, `shot` and `save-artifact`.
- **B2 — scroll stopped on SPA layouts.** Edge detection read `window.scrollY`, which never changes when an inner container scrolls (Gemini, most apps): asked to scroll 3000 px it scrolled 452 px and stopped as "stuck" after 2 ticks. Scrolling now finds the real scroll container under the pointer and tracks *its* scroll offset (like browser scroll chaining, an ancestor with room wins over one already at its edge).
- **B3 — `--typos=on|off|auto` was dead.** `humanOpts` never forwarded it, so `humanType` always ran in `auto`. It is now validated and forwarded for `fill`, `type`, `type-focused` and the paste typing fallback (`--typos=off` on a ~120-character text produces zero Backspace keydowns).
- **B4 — `dblclick` never double-clicked.** The human click loop pressed every click with `clickCount` 1, so pages saw two single clicks (`detail: 1`) and no `dblclick` event. Each press now carries its ordinal.

- **B5 — every dwell and gap rode the OS timer tick.** All waits went through Node's `setTimeout`, which fires on the OS timer tick: ~15.5 ms on this Windows machine (`sleep(1/5/10)` → 15.5 ms, `sleep(17/24)` → 31, `sleep(33)` → 46.5, `sleep(47)` → 62, `sleep(70)` → 77.5). Measured with page-side listeners: click dwells (pointerdown→pointerup) of 46.6, 62, 77.2, 92.9 and 123.9 ms — 86% within ±1 ms of the 15.625 ms lattice — and intra-flick wheel gaps of 31 / 46.5 ms; a key-up stamped "key-down + dwell" but dispatched at the next tick reached the handler up to 16 ms after its own `timeStamp` (28 of 86 key events more than 8 ms), where real discrete input shows ~0.2 ms. New `src/timing.js`: `preciseSleep` / `preciseSleepUntil` wait with a timer for the bulk and a cooperative `setImmediate` spin for the last tick — never a synchronous busy loop, several pages share one daemon event loop; the timer granularity is measured in the background at daemon start (16 ms assumed on Windows, 2 ms elsewhere until then) as the upper quartile of 15 consecutive `setTimeout(1)` gaps — not the median, which the browser launching at the same moment drags down (it wakes the loop between ticks): over six daemon starts the median gave 11 / 15.5 / 11.5 / 15.5 / 15.5 / 11.5 ms for a 15.5 ms tick, and a timer budgeted for 11.5 ms ended ~15% of the sleeps 0.5–1.1 ms late (budgeted for 16: at most 0.2 ms). `human.sleep` is precise; `human.coarseSleep` (plain `setTimeout`) is used only for polling that does not end in an input event (the paste verify loop, scroll settle checks, the `calibrate-wheel` overlay refresh, the `select` read-back, `wait`). Every wait followed by an input event is precise: click settle, dwell and inter-click gap, modifier lead and lag, typing delays, key dwell, the autorepeat schedule, Shift lead and lag, the layout-switch chord, wheel gaps, drag pre-hold and settle, path frame pacing (now on an absolute schedule, so the dispatch round trip counts against the frame), `select` arrows and Enter, think times, touch frames, file-drag frames. Discrete events — key down/up, autorepeats, Shift, touch — no longer carry a timestamp of ours: Chrome stamps them at dispatch, like real input, and the "dwell encoded in the key-up timestamp" mechanism is gone. The human-path presses that went through Playwright's `delay` (the no-CDP typing fallback, keys the emitter does not know, the macOS shortcut path) are now down → precise sleep → up.
- **B6 — pointer sub-samples were stamped from the wall clock.** The coalesced sub-samples are the one place that carries an explicit CDP timestamp. Measured: Chrome passes the stamp through unclamped (an event stamped now+50 ms was handled 37.7 ms *before* its own `timeStamp`, +500 ms → 483 ms before) and converts it with a Unix-epoch → TimeTicks offset that is frozen once per browser process, so stamps derived from `Date.now()` (1 ms truncation jitter, slewed or stepped by time sync and resume) can drift away from Chrome's clock over uptime; over 12 minutes a monotonic anchored clock was perfectly stable (lag 0.8 ms in all 24 rounds) while `Date.now()` stamps jittered 0.7–1.3 ms. Stamps now come from `timing.nowSec()`, a monotonic clock anchored to the wall clock at one instant, and the daemon pins Chrome's offset to that anchor right after launch with one timestamped `mouseMoved` to (0, 0) on its own blank keeper page (never a website; skipped if the profile restored a site into the first window; a failure is logged, not fatal). The last sub-sample of a burst is "now", none is later, and they are strictly increasing, also from one burst to the next.
- **B7 — pointer coordinates were off the device-pixel grid.** A real mouse reports physical pixels: integer `clientX` at `devicePixelRatio` 1, multiples of 1/dpr otherwise. Measured: 16 of 569 pointer coordinates of a click grid were fractional (e.g. `pointerdown`/`pointerup` `clientX` 169.5018 — `pointInBox` / `jitterPoint` → Playwright's `mouse.move`/`down`); Playwright passes a float straight through (`mouse.down` at (120.43, 60.29) → `PointerEvent.clientX` 120.43000030517578), and the burst sub-samples were rounded to whole CSS pixels, which is off the grid at dpr 1.5 (101 css px = 151.5 device px, unreachable). Every pointer coordinate the daemon dispatches is now snapped with `q(v) = round(v · dpr) / dpr`, dpr being the page's current `devicePixelRatio` (cached per page, refreshed whenever the viewport is measured, fetched at the start of a move when unknown): burst sub-samples, every Playwright `mouse.move`/`down`/`up` target (the idle-jitter moves, the final settle move, the pointer sync), the initial pointer position, overshoot points, the wheel's position, pointer and HTML5 drags, `drop-files` points and the `--raw` coordinate commands (`click-at`, `hover-at`, `drag-at` — the latter steps on the grid too, Playwright's own `steps` interpolation being fractional). The tracked pointer holds the snapped value, and `landedAt` / `css` in responses show the snapped point. Touch coordinates are not snapped (a digitizer reports sub-pixel positions), and the raw *selector* commands that Playwright positions itself (`click <selector> --raw`, …) stay robotic, as documented.
- **B8 — field clearing pressed the wrong keys.** `humanClearField` used `page.keyboard.press('Control+A')`, which names the wrong `key` when the page's layout state is Russian (`humanPress` presses the physical key), uses Control even on macOS (where Ctrl+A moves the caret and the field is not cleared) and sleeps its `delay` on the timer tick. It now goes through `humanPress`: Cmd+A on macOS, Ctrl+A elsewhere, then Delete or Backspace. (The macOS shortcut path also names a character of another layout by its physical code now — Playwright knows only the US layout's characters.) Also fixed there: the randomised selection gesture had an 8% "no click, move only" draw, which is only right for a field that already has the focus — on any other, select-all, the delete key and the text that follows went to whatever was focused (measured: in 1 of 14 rounds `fill` cleared and typed into the textarea that had the focus before). A field without the focus now always gets a click.
- **B9 — `calibrate-wheel` put its overlay into whatever page was open.** Measured: it injects a visible DOM overlay ("NativeWright wheel calibration") that the site's own scripts can see. It now refuses, before injecting anything, unless the page is `about:blank`, a `data:` or `file:` URL, or http(s) on `localhost` / `127.0.0.1` / `[::1]`; the error says why (the overlay is visible to the site's scripts) and how (`nativewright new --label=calibrate` starts on `about:blank`, then `calibrate-wheel --page=<id>`). `--simulate` is held to the same rule.
- **B10 — `drop-files` offered only "copy".** Measured: `dragOperationsMask: 1` gave `dataTransfer.effectAllowed` `'copy'`, while a file manager's drag offers copy | link | move (`'all'`); with `'copy'` a page that answers `dropEffect = 'move'` gets no drop at all. The mask is now 19 (Copy 1 | Link 2 | Move 16).
- **B11 — a typed paste fallback could type for hours.** A paste that falls back to typing (headless, or a busy clipboard) typed whatever it was given — with `--from-file` up to 5 MB, at ~190 ms a character, while the page's command queue was blocked. Over 2000 graphemes it now refuses without typing anything: the error names the fallback reason, says how long typing it like a human would take (about N minutes, from the engine's own pace, which a sanity check re-measures) and suggests a headed daemon with an empty or plain-text clipboard, or `fill --raw` for bulk text.
- **B12 — a start from a git clone hijacked the install pointer.** Every daemon start rewrote `<data root>/install.json`, so one start from a checkout sent the tools that find the CLI through it (when `nativewright` is not on their PATH) to unreleased working-tree code on the real profile. The pointer is now written only when there is none, when the existing one points at a script that no longer exists, or when the running script is an installed package (a `node_modules` segment in its real path); a start from anywhere else — a checkout, `npm link` included — never replaces a valid pointer to another path, and logs one line when it declines.
- **B13 — a click could land on a textarea's resize grip.** Found by the CI-like run (bundled Chromium, headless), not by a spec item: `pointInBox` is a Gaussian around the middle clamped to a 2–6 px margin, so on a wide `<textarea>` the clamp piles mass onto the right edge; the press then starts a resize drag and the field never gets the focus, and the text that follows goes to whatever is focused. Measured: 1 of 80 live clicks on a 366×76 textarea landed at (380, 133) in a box spanning x 20–386, y 70–146 and `document.activeElement` stayed `BODY`; seeded, 1.35% of 20 000 picks fall in the 18 px bottom-right corner of that box. `click`, `dblclick`, `rightclick` and the field-clearing click now re-pick a point when the first one is inside that corner of an element whose computed `resize` is not `none` (and that scrolls or clips, which is what makes the browser draw a grip); anything else is untouched, and an explicit `--at` is never moved.

## [2.1.0] — 2026-10-16

### Added
- **Named profiles.** `--profile=<name>` on any command (or `NATIVEWRIGHT_PROFILE=<name>`) selects a separate browser identity that runs as its own daemon, with its own Chrome profile, cookies, extensions, lockfile and logs under `<data root>/profiles/<name>/`. The default profile is unaffected. Names: letters, digits, `-`, `_`, up to 32 chars. A named profile always owns its own Chrome profile directory (`NATIVEWRIGHT_USER_DATA_DIR` applies to the default profile only, so a machine-wide setting can't make two daemons fight over one profile lock).
- `status`, `state` and the lockfile report the active `profile`.
- **`nativewright-vpn` skill** — the "blocked by IP" workflow: detect a per-IP limit, move the task into a dedicated `vpn` profile, turn its browser VPN on, verify the new exit IP, retry there; with a version guard, coordination rules for shared VPN state, and a 3-country cap.
- `nativewright` and `nativewright-login-bootstrap` skills document profiles.

### Fixed
- Smoke test no longer depends on an external site: it serves its own fixture page from a child process (example.com dropped its `<h1>` and asks not to be used for testing, which broke the test and CI).

## [2.0.0] — 2026-09-02

Multi-agent release. Any number of clients can now share one daemon safely,
each with its own page in its own window. This changes the command contract
(see **Removed** / **Changed**) — hence the major bump.

### Added
- **Stable page ids.** `new` returns `p1`, `p2`, … — an id that never changes for the page's lifetime and is never reused, even when other pages close. `new` accepts `--label=<name>` (shown by `pages` so a person can tell whose window is whose) and `--window=false` to open a tab instead of a window.
- **Explicit, atomic page targeting.** Every page command takes `--page=<id>`; the daemon binds the command to that page inside the page's own serialized queue. Commands on different pages run concurrently. Responses echo the targeted page: `{ok, page, result}`.
- **Ambiguity refusal.** With more than one page open and no `--page`, the daemon refuses with a clear error instead of guessing. A lone page needs no flag. `NATIVEWRIGHT_PAGE=<id>` pins a default page for a shell; the REPL pins the page it creates (`use <id>` / `use` to change or clear).
- **A window per page.** `new` opens each page in its own browser window (`Target.createTarget newWindow`). A page in its own window stays a foreground page — `visibilityState: 'visible'`, timers and rAF running — even when other windows overlap it. Windows are cascaded so a person sees them apart. Falls back to a tab if the browser-level CDP session is unavailable.
- **Per-page state.** Frame scope (`frame`), dialog policy (`dialog`), and console / network / download buffers are now per page instead of daemon-global.
- **Artifacts next to the caller.** `shot`, `save-artifact`, and captured downloads are written under the requesting client's working directory (`./artifacts/`), so agents in different projects don't mix output. `upload` and `eval-file` paths resolve relative to the caller too. `NATIVEWRIGHT_ARTIFACTS_DIR` still forces one location.
- **Lease-based lifecycle.** Clients `close --page=<id>` when done. When no pages have been open for `NATIVEWRIGHT_IDLE_EXIT_MS` (default 10 min; `0` = never) the daemon exits gracefully, flushing the profile. `stop` refuses while pages are open; `stop --force` shuts down regardless. A minimized internal keeper window keeps Chromium alive between leases.
- `status` now reports `pageCount` and the open pages (id, label, url); `--verbose` adds the idle-timer state. Log lines are tagged with the page they acted on (`[p3] fill ok 6272ms`).
- Env vars are accepted under both `NATIVEWRIGHT_` and the legacy `PATCHRIGHT_` prefix, so neither spelling is silently ignored.

### Changed — human-behavior layer
- **Pointer coalescing.** Mouse motion is dispatched as per-frame bursts of sub-samples via CDP with explicit monotonically increasing timestamps, so `PointerEvent.getCoalescedEvents()` returns several distinct, correctly ordered samples per `pointermove` (scaling with motion speed) instead of always exactly one. Falls back to the classic per-point path if a CDP session can't be created.
- **Keyboard.** Keystrokes are emitted via CDP keyed on the physical `code`, with explicit `ShiftLeft` keydown/keyup around capitals and shifted symbols (Shift is held across consecutive shifted characters, as a typist does). The typo path uses the same emitter. Per-key dwell is encoded in the keyUp timestamp, so observed dwell is a continuous value rather than one snapped to the OS timer tick. Unmapped characters (emoji, accented letters, CJK) fall back to the previous press path.
- **Field clearing.** The select-all gesture before typing varies per call (triple/double/single/no click, then `Ctrl+A`, then `Delete` or `Backspace`) instead of one fixed sequence.
- **Think-time.** The 15% "fast hand-off" branch now returns a brief non-zero pause instead of exactly 0 ms.

### Removed
- `switch <index>` — there is no shared active page anymore. Calling it returns an error explaining `--page=<id>`.
- Numeric page indices. `pages` reports ids.
- `close-page` is kept as an alias of `close` but is deprecated.

### Migration
1. After `start` / `wait-ready`, call `nativewright new --label=<task>` and keep the returned `page` id.
2. Add `--page=<id>` to every page command (or export `NATIVEWRIGHT_PAGE=<id>` in a persistent shell).
3. Replace `switch N` + command with the command itself carrying `--page=<id>`.
4. Replace the end-of-task `stop` with `close --page=<id>`. Use `stop` only as an administrative shutdown (`--force` if pages are open).
